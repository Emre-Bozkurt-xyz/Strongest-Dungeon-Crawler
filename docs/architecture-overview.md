# Strongest Dungeon Crawler - Architecture Overview

Last updated: 2026-01-25

This is a code-driven overview of the current architecture. It prioritizes what is actually in src/ over older design docs. When docs and code diverge, this file reflects the codebase.

---

## 1) High-level structure

Entry points
- Server: `src/server/init.server.luau`
- Client: `src/client/init.client.luau`
- Shared: `src/shared/` (types, networking, utilities)

Top-level folders
- `src/server/` gameplay authority (combat, stats, skills, NPCs, services)
- `src/client/` prediction, UX, UI, animation and FX
- `src/shared/` contracts and shared utilities (networking, stat types, skill types)

Key architectural decisions
- EntityId-based identity for all gameplay state (players and NPCs share the same ID format).
- Server authoritative gameplay with client prediction and reconciliation for UX.
- Unified session-based skill execution (SessionManager + SessionMirror).
- Event-driven networking via a centralized Dispatcher and explicit channel registry.
- Stat queries run through a mediator/observer pipeline to support modifiers and caching.

## 2) Shared infrastructure

### Networking
Path: `src/shared/Networking/`

What it does
- Defines channels and QoS in `Channels.luau`.
- Provides a `Dispatcher` abstraction for events and request/response flows.
- Creates singletons for client/server dispatchers (`Networking.client()` / `.server()`).

Key files
- `Channels.luau`: canonical channel definitions (Skills, Stats, FX, SkillSession, TimeSync, etc).
- `Dispatcher.luau`: envelope + QoS + request/response dispatch.
- `ChannelRegistry.luau`: loads channel definitions at startup.

Notes
- Channel definitions are auto-loaded when the Networking module is required. You do not need to manually register channels in services.
- Channel names/intents/events are now centralized in `src/shared/Networking/ChannelNames.luau` and ChannelRegistry asserts uniqueness at load time.
- Bootstrap diagnostics are centralized in `src/shared/BootstrapDiagnostics.luau` and emit startup warnings when core services fail to load.

### Shared skill types
Path: `src/shared/skills/`

Key files
- `SessionTypes.luau`: SkillSession contract for server and client.
- `AttemptState.luau`: lifecycle states for predicted skill attempts.
- `SkillTimingResolver.luau`: resolves tempo and duration scale based on skill tags and stats.
- `ClientSpec.luau`: client-facing visuals (animations, FX, UI labels).

### Shared stat types
Path: `src/shared/StatTypes.luau`, `src/shared/StatTypeUtil.luau`

Key files
- `StatTypes.luau`: canonical stat names and entity stat structure.
- `StatTypeUtil.luau`: serialize/deserialize stats and apply deltas.

### Entity utilities
Path: `src/shared/EntityUtils.luau`

What it does
- Helpers for determining faction and other entity-level utilities used by systems like projectiles.

## 3) Server systems

### 3.1 Initialization and orchestration
Path: `src/server/init.server.luau`

The server startup does the following:
- Runs a bootstrap registry (`src/server/Bootstrap.luau`) that defines ordered startup for core systems.
- Starts RegenerationService, SessionManager heartbeat, EntityInfoService, and TimeSyncService via the bootstrap.
- Initializes NPCManager and component updates via the bootstrap.

Potential improvement
- Dev/test setup is now in `src/server/dev/InitDev.luau`; keep expanding this to avoid production drift.

### 3.2 Registrar (entity registry)
Path: `src/server/Services/Registrar.luau`

Responsibilities
- Registers Models with EntityId and maps EntityId to Model/Player.
- Provides lookup APIs used by almost every system (Stats, Skills, StatusEffects, NPC).

Current design choices
- Stores EntityId on models as an attribute.
- Uses CollectionService tag "Entity".

Potential improvement
- `getEntityId(model)` and `getPlayerId(player)` currently scan maps linearly. Maintain reverse maps (model -> id, player -> id) to avoid O(n) scans.

### 3.3 Stats system
Path: `src/server/Stats/`

Core components
- `StatsManager.luau`: entity stat storage, modifier application, delta replication.
- `StatsMediator.luau`: observer pipeline + caching for stat queries.
- `SkillMediator.luau`: skill-specific stat query resolver (cost, damage, etc).
- `AttributesManager.luau`: RPG-style attributes and scaling.
- `SkillModifierRegistry.luau`: per-entity skill modifier registry.

Key decisions
- Stats are queried via StatsMediator which supports observers, caching, and per-context metadata.
- Server emits deltas via the Networking Dispatcher (channel: Stats).
- Resource pools (health/mana/stamina) are regenerated by RegenerationService.

Potential improvement
- Stats and Skill metadata updates are mostly pull-based; metadata updates are manual. Add a stat-change signal that can notify SkillMetadataService to refresh specific skills.
- Some services use `tick()` while others use `os.clock()`. Standardize on `os.clock()` for deterministic timing.

### 3.4 Skills framework (server)
Path: `src/server/SkillsFramework/`

Core components
- `SkillsManager.luau`: entry point for skill use requests and gating.
- `SessionManager.luau`: unified execution session state with heartbeat expiry.
- `CooldownService.luau`: authoritative cooldown/GCD tracking.
- `SkillTimingService.luau`: resolves tempo using skill tags and entity stats.
- `SkillMetadataService.luau`: computes cost/timing metadata for clients.
- `HitboxService.luau`: cone/sphere/box/raycast queries for melee and AoE.
- `AttackResolver.luau`: builds attack packets and applies modifiers.

Key decisions
- SessionManager is the single source of truth for skill execution and combo steps.
- SkillsManager uses SessionManager to create and advance sessions.
- Combo windows are scheduled based on client-provided inputTime; server validates against those windows without canceling the session.
- SkillRequestUse is the single request entrypoint for skill execution (legacy SkillsRequest removed).

Potential improvement
- Skill execution timing still uses `task.delay` inside individual skills. Consider unifying all step scheduling through `Timeline` or a central scheduler (similar to SessionManager heartbeat) to improve traceability and cancellation.
- There is both `ProjectileService` in Services and in SkillsFramework with older `_ProjectileService` leftover. Consolidate to a single projectile pipeline and remove the legacy module.

### 3.5 Combat and damage
Path: `src/server/Services/CombatService.luau`

Responsibilities
- Applies damage via stats, armor/crit/dodge, and shields.
- Emits combat events to clients.
- Integrates with StatusEffectsService and StaggerSystem.

Key decisions
- Damage is resolved through stats and modifiers, then applied to resource pools.
- Attack composition uses AttackResolver to allow modifiers to mutate packets.

Potential improvement
- Attack composition is separate from skill cost resolution. Consider a unified query contract for both cost and damage to simplify modifier authoring and reduce duplicate metadata plumbing.

### 3.6 Status effects
Path: `src/server/StatusEffects/StatusEffectsService.luau`

Key features
- Stacking policies (aggregate, multi, charges), duration policies, and tick modes.
- Action blocking integration (emit StatusEffectBlocking to clients).
- Effect definitions loaded from `EffectsIndex.luau`.
 - ActionPermissions only queries StatusEffectsService + Health; execution locks are handled by SkillsManager.

Potential improvement
- Debug logging is enabled by default; consider a central debug config to avoid noisy servers.

### 3.7 NPC system
Path: `src/server/NPCService/`

Key parts
- `NPCManager.luau`: registration, entityId assignment, stats registration.
- `ComponentManager.luau`: orchestrates component updates and avoids circular dependencies.
- Components: `Movement`, `Combat`, `Behavior`, `Damageable` (folder + attribute based).

Key decisions
- Components are stored as Folders + Attributes for easy inspection and low overhead.
- Update loops are centralized in ComponentManager.

Potential improvement
- Component state is spread across Attributes and runtime tables. Add a shared data schema per component to reduce inconsistencies and make serialization easier.

### 3.8 Entity info streaming
Path: `src/server/Services/EntityInfoService.luau`

What it does
- Streams presence data to clients based on Perception stats (distance and tier).
- Sends presence deltas at a fixed tick rate.

Key decisions
- Registrar owns entity identity; EntityInfoService only reads from Registrar and does not maintain separate id maps.

### 3.9 Projectile system
Path: `src/server/Services/ProjectileService.luau`

Key decisions
- Server is authoritative for spawn; clients simulate visuals from deterministic recipes.
- Supports linear and parabolic movement with attach/spawn patterns.

Potential improvement
- A second projectile module (`_ProjectileService.luau`) exists. Consolidate and delete the unused path.

## 4) Client systems

### 4.1 Client bootstrap
Path: `src/client/init.client.luau`

Startup flow
- Runs a bootstrap registry (`src/client/Bootstrap.luau`) that defines ordered startup for client systems.
- Initializes AssetLoader, TimeSync, SessionMirror, ActionPermissions mirror, Stats/Attributes, and UI controllers.

Potential improvement
- Similar to server, init mixes production setup with ad-hoc test toggles. Consider central config + feature flags.

### 4.2 Skills framework (client)
Path: `src/client/SkillsFramework/`

Core components
- `SessionMirror.luau`: client mirror of server SessionManager state.
- `SkillPacer.luau`: local pacing of execution, combo windows, cooldown/GCD.
- `SkillsClient.luau`: binds session changes to FX/animation cleanup.
- `CooldownClient.luau`: local cooldowns; server cooldowns are ignored for UX gating.
- `AttemptStore.luau`: tracks predicted attempts and reconciliation.
- `PredictionController.luau`: centralizes prediction lifecycle (attempts + session prediction).
- `SkillMetadataClient.luau`: caches server-computed metadata.

Key decisions
- Client predicts skill execution and plays FX/animation immediately.
- Client uses local pacing; server validates only for correctness.
- Session events reconcile client state but do not drive local gating.
- ActionPermissions on client only mirrors status-effect blocking; SkillPacer owns execution gating.
- SkillPacer is the sole local gate for execution timing; early inputs are rejected until the window opens.
- Skill metadata is refreshed on stats/attributes/skill-mediator changes and periodically; updates carry per-skill versions to avoid stale overwrites.

Potential improvement
- Prediction logic is split across BaseSkill, SkillPacer, AttemptStore, and SkillsClient. Consider formalizing a PredictionController to simplify reconciliation logic and avoid cross-module coordination.

### 4.3 Animation and FX
Path: `src/client/Animation/` and `src/client/fx/`

Key components
- `AnimationCoordinator.luau`: skill marker event hub and session-bound track cleanup.
- `AnimationPlayer.luau`: loads and plays animations, supports duration scaling.
- `FXPlayer.luau`: spawns and manages FX locally.
- `Replicator.luau`: relays FX to other clients via server.
- `ImmediateHitFeedback.luau`: local hit feedback (sound/flash) on markers.

Key decisions
- FX is client-authored for immediate feedback and replicated to others.
- Session-based cleanup stops FX and animation on cancel/complete.

Potential improvement
- FX ownership is spread across BaseSkill and Replicator. Consolidate lifecycle rules to reduce duplicate cleanup logic.

### 4.4 UI
Path: `src/client/ui/`

Key components
- `SystemPanelHandler`: stats and attributes UI wiring.
- `SkillSlotUI` and `SkillSlots`: UI and input binding for skills.
- `DamageNumberController`: floating damage numbers.
- Status preview, stagger, and overhead health controllers.

Potential improvement
- A number of controllers are initialized ad-hoc in init.client.luau. Consider a UI bootstrap that declares dependencies and order.

### 4.5 Input
Path: `src/client/input/`

Key components
- `InputManager`: map actions to callbacks.
- `ActionConfig`: action definitions.
- `Inputs.client.luau`: binds action names to skill slots and UI toggles.

Potential improvement
- Expose input remapping or config-driven bindings to reduce hard-coded actions.

## 5) Core gameplay flows

### Skill execution flow (player)
1. Player input triggers `SkillsClient.useSkill` (from InputManager + SkillSlots).
2. `BaseSkill:canUseLocally` checks SkillPacer, cooldown, and resources.
3. Client predicts session and starts animation/FX immediately.
4. Client sends `SkillRequestUse` with `inputTime` (server time domain).
5. Server `SkillsManager` validates ActionPermissions and cooldowns, then updates SessionManager.
6. Server skill logic runs (hitboxes, damage, status effects).
7. SessionManager emits session events; client mirrors them via SessionMirror.
8. Client reconciles prediction (cancel or keep), and SkillPacer enforces local pacing.

### Damage flow
1. Skill hit logic builds an attack query (AttackResolver).
2. CombatService applies damage to resource pools via StatsManager.
3. StatusEffectsService may apply effects; StaggerSystem may apply stagger.
4. Combat events replicate to clients for hit feedback and UI.

### Stat update flow
1. Server StatsManager computes stats and resources.
2. Deltas are emitted via Stats channel.
3. Client StatsClient applies deltas and updates UI.

## 6) Known fault lines and simplification opportunities

1. Mixed scheduling models
   - Skills use a mix of `task.delay`, `Timeline`, and SessionManager heartbeat.
   - Recommendation: pick a single scheduling model (Timeline or SessionManager) for skill timings.

2. Bootstrap mixing production and test data
   - `init.server.luau` hardcodes skill grants and test modifiers.
   - Recommendation: move test setup into a dev-only feature flag or a Testing module.

3. Duplicate or unused systems
   - `_ProjectileService.luau` and `SkillsFramework/ProjectileService.luau` coexist with Services/ProjectileService.
   - Recommendation: consolidate and delete the legacy path.

4. Registrar lookup cost
   - Linear scans for `getEntityId` and `getPlayerId`.
   - Recommendation: add reverse maps to achieve O(1) lookup.

5. Metadata refresh triggers
   - SkillMetadataService updates are manual; metadata does not auto-refresh on stat changes.
   - Recommendation: add a stat-change observer that refreshes only affected skills.

6. Time source inconsistencies
   - Some systems use `tick()` while others use `os.clock()`.
   - Recommendation: standardize on `os.clock()` for deterministic timing.

7. UI and system initialization order
   - Client init performs ad-hoc initialization with implicit dependencies.
   - Recommendation: use a bootstrap registry for deterministic initialization order.

## 7) Suggested future refactors (optional)

- Create a centralized "GameplayClock" module to unify time usage and provide debugging hooks.
- Introduce a small dependency injection layer for services to avoid hard-coded requires in init scripts.
- Formalize an event schema for skill and combat telemetry to simplify debugging and profiling.
- Consolidate modifiers (stats, skills, attacks) behind a single registry API to reduce mental overhead.

- `src/server/SkillsFramework/` skill execution, session management, cooldowns, metadata
- `src/server/Stats/` stat storage, modifiers, attributes, mediator
- `src/server/Services/` combat, regen, projectiles, time sync, registrar
- `src/server/NPCService/` NPC component system and AI
- `src/server/StatusEffects/` status effect stacking and blocking
- `src/client/SkillsFramework/` prediction, pacing, skill UI
- `src/client/fx/` FX and animation playback
- `src/client/ui/` UI controllers and HUD
- `src/shared/Networking/` dispatchers and channels
- `src/shared/skills/` shared skill contracts and timing
